# Продолжение разработки

Приоритет владельца от 2026-11-04: ИИ интегрируется в последнюю очередь.
Сейчас развивать собственную ОС и универсальные средства управления процессами,
ресурсами, правами, событиями и действиями сервисов. Они проверяются обычными
тестовыми клиентами без весов/модели. Прототип v0.0.17–18 сохранить optional,
не развивать inference/чат/подбор моделей до готовности основания. Контракты,
текущие ограничения и критерий готовности — system-control.md.

После v0.0.18 начата основа многоклиентного FS: backend fs3_handle_client
отделяет доверенную client identity от запроса, защищает draft/commit/abort;
fs3_client_closed откатывает только транзакцию указанного владельца без IO.
Сервис получает sender через receive_wait_from из метаданных ядра. Пока это
индекс задачи и один активный FS-клиент; устойчивой сессии с generation и
автоматической доставки client-closed ещё нет. Новые host-тесты проверяют
владение, изоляцию draft, очистку без IO, полный 64-битный token и poisoned.
Проверены 18 host FS3 тестов и гостевые boot128/file-SDK/supervisor/FS3 без модели;
всё PASS, отчёт build/system-control-foundation/result.json. Сборка на рабочей
VMware остаётся проверенным тегом v0.0.18; новый backend пока только в исходниках
и изолированных тестовых образах. Следующий шаг — устойчивые логические сессии
и раздельные очереди ответа, затем фоновый lifecycle обычных .nos.

Текущий устойчивый результат — v0.0.18: фоновый AI, отдельные очереди и
блокирующее ожидание. Полный check-release --desktop --ai (19 этапов), затем
точечная проверка учёта cache, supervisor/SDK/FS3, native compiler и новый
test_build_variants прошли. Последний добавлен двадцатым этапом в --ai.
Пользователь разрешил продолжать
самостоятельную работу, пока он не дома, без ожидания подтверждений для уже
разрешённых действий. Не повторять вопрос об архитектуре: выбрано микроядро,
.nos — ELF64 с локальным ABI, ОС собственная. Вся исходная цель не завершена.

Есть UEFI/Limine x86-64, собственная память/таблицы/исключения, ring 3 и FPU,
таймер, IPC с правами, файловый сервис FS3, транзакции, supervisor и нативные
C/ASM -> .nos, SDK из 21 файла, куча 2 МиБ. Проверены холодный старт и компиляция.

Новый GUI: русский/английский ввод, UTF-8, выделение, внутренний clipboard,
восемь шагов undo/redo, Home/End/Delete/PageUp/Down, разворот Notes. Files открывает
текст и выбирает .nos; Programs запускает его с аргументами, захватывает stdout,
показывает exit/fault/time-limit. File grant по умолчанию off, сбрасывается при
смене executable. Сбой приложения сохраняет desktop и несохранённую заметку.
Build C готовит compiler.nos + source/output; права на файлы пользователь включает
явно. Bootstrap устанавливает отсутствующие hello/compiler без замены файлов.

Важное ограничение: это bounded foreground launcher. Desktop SUSPENDED на время
дочернего процесса; по окончании восстанавливаются его адресное пространство,
куча, FXSAVE и IPC-клиент. Встроенные окна пока в одном процессе. Нет общего
менеджера процессов, параллельных GUI-приложений, stdin и per-file grants.
Диагностическая консоль в ядре. Нет C++, каталогов и общего менеджера процессов.

В 0.0.17 добавлен настоящий optional CPU inference runtime. Источник — pinned
llama2.c MIT, профиль stories260K/MIT (HF model card сохранён), 1,062,799-байтовый
boot pack, tokenizer512, KV512. Веса не в Git, SHA/revision — models.lock.json.
setup-ai-demo.py получает их в tools/, сборка с NEUROOS_AI_DEMO=1 проверяет хеши.
В runtime нет файловых/ATA/desktop/launch прав: только приватный AI IPC и read-only
model cap. GUI syscall14 приостанавливает desktop, отдельные user runtime/client
исполняют forward и возвращают текст, затем прежний desktop возобновляется.
Syscall17 выдаёт только выбранный boot pack и только runtime. Есть cache, Unload,
контролируемый restart после реальной #PF. Пройдены точные token traces против
host oracle и GUI с 128 МиБ. AI не пишет файлы и не выполняет действий по тексту.
Это учебная английская continuation-модель, а не выбранный основной помощник.
Нет истории диалога, memory/Agent Manager, моделей произвольного профиля и GPU.

0.0.16, 0.0.17 и 0.0.18 собраны и проверены; версия исходников — main/v0.0.18.
Рабочая VMware открыта с 0.0.18 и AI-модулями. Перед каждой заменой сохранён
SHA-проверенный диск. В 0.0.16 добавились только отсутствующие hello/compiler;
при 0.0.17 и 0.0.18 весь data-flat.vmdk (25 файлов) остался побайтово прежним.
В 0.0.18 ELF LOAD всех десяти программ, объект process.o и model pack совпали
с тестовыми. В compiler.nos устранён вариантный путь __FILE__; полный бинарник
совпал в normal/desktop-ai/bootstrap-desktop-ai. Все проверки —
validation.md, интерфейс — desktop.md, inference — ai-demo.md.

В 0.0.18 GUI использует syscall15 START/POLL/CANCEL/UNLOAD без сохранённого userptr.
FS/desktop остаются на 0/1, AI runtime/client на 2/3; cache перебинживает cap при
переходе GUI/console. Sleep12 теперь SLEEPING с deadline; receive_wait16 — WAITING,
пробуждение по сообщению/смерти peer, проверка writable до блокировки. Пауза не
равна смерти процесса. Idle сервисов/desktop позволяет HLT. Cache нормализует
незавершённый receive в retry -11 при парковке. Native syscall13 во время AI
отклоняется busy, чтобы прежний foreground путь не затёр активные задачи.
Ctrl+Alt+G генерирует из любого окна; Esc отменяет в AI, Ctrl+Alt+Q — Console с
прежним подтверждением dirty. Закрытие desktop отменяет активный AI, страницы
обоих процессов освобождаются. Проверка test_ai_background.py замедляет реальный
QEMU icount6, проверяет порядок save<completion, cancel/restart, переход cache
из background в console и выход из desktop во время работы + PMM.

Следующий конкретный шаг после завершения релиза: lifecycle/reap обычных .nos
в фоне и раздельные очереди ответов FS по клиенту. У FS3 транзакция пока общая;
нужны устойчивая логическая IPC/FS-сессия, маршрутизация ответа и доставка её
закрытия в новый owner-aware backend, прежде чем пускать desktop и ребёнка к
одному сервису одновременно. Учесть временные fsclient-задачи kernel broker:
новый helper на очередной RPC не должен становиться другим владельцем транзакции.
Blocking receive уже есть.
Не выдавать ребёнку права desktop/input/launch или ATA-портов; сохранять прежний
ограниченный launcher как проверенный путь до прохождения новых тестов.

навигацию. Не объявлять весь проект готовым после очередного build/test batch.
