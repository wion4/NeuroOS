# Системные средства управления и порядок интеграции ИИ

Приоритет подтверждён владельцем 2026-11-04: сначала полноценная ОС и её средства
управления, интеграция моделей и алгоритмов инференса — последний этап. Нужные
системные интерфейсы разрабатываются вместе с соответствующей подсистемой ОС.
До готовности основания модели не нужны для проверки этих интерфейсов.

Прототип v0.0.17–18 сохраняется как optional эксперимент. Развитие генератора,
подбор новых моделей, весов, обучения и интерфейса чата отложены. Его специальные
вызовы 14/15/17 не считаются готовым универсальным API управления ОС.

## Граница полномочий

Будущий runtime генерирует данные в пользовательском процессе. Системные действия
выполняют обычные сервисы по структурированным запросам с проверяемыми правами.
Системные инструменты доступны также обычным C/ASM программам и тестовым клиентам.
Ни текст модели, ни поле sender в запросе не выдают полномочия. Источник прав —
ядро и доверенная служба делегирования; проверка происходит у исполнителя.

Наблюдение и изменение требуют разных прав. Выданные права должны ограничивать
объекты, операции, срок и ресурсы задачи. Отзыв права и отмена работы должны
останавливать новые побочные эффекты; уже подтверждённый commit нельзя выдавать
за отменённый. Общий откат произвольных внешних действий не предполагается.

## Что готовим до интеграции модели

| Подсистема | Необходимые средства управления | Текущее состояние |
|---|---|---|
| Процессы | Устойчивые идентификаторы, запуск, запрос статуса, отмена, ожидание и reap | В 0.0.19 есть desktop-owned START/POLL/CANCEL/REAP; общий manager и несколько jobs впереди |
| IPC | Проверка cap/буферов, независимые сессии и ответы, блокировка/пробуждение, разрыв связи | Есть логические FS-сессии и раздельные ответы desktop/ребёнку; несколько RPC одного клиента впереди |
| Файлы | Объектные права, транзакция владельца, освобождение сессии, проверяемый commit | В 0.0.22 есть права по 4 именам/операциям, COW/CRC/owner/cleanup; stable handles и живой отзыв впереди |
| Память | Лимиты, безопасные разделяемые буферы, RO mapping больших файлов, освобождение после сбоя | Частные страницы/NX и 2 МиБ heap есть; большие mappings и handles впереди |
| Задачи | Бюджеты CPU/памяти/IO, дедлайны и отмена без остановки GUI | В 0.0.21 loading также в user space с Stop/wall deadline; CPU budget есть, расширенные квоты впереди |
| События | Структурированные события процесса/операции, подписки с правами и обнаружением потерь | В 0.0.20 есть read-only observer native jobs, sequence/cursor/lost; общие scoped subscriptions впереди |
| Журнал | Кто запросил действие, на каком объекте, результат/ошибка/версия и связь с задачей | RAM-кольцо 64 lifecycle-записей: owner/job/result/resources; постоянный аудит операций/boot ID впереди |
| История/индексы | Версионированные записи, оригиналы отдельно от производных данных, поиск, экспорт и восстановление | Файлы и транзакции есть; общего хранилища записей/индексов ещё нет |
| Приложения/GUI | Запрос доступного состояния и семантических действий по IPC с правами | Есть desktop/input API одного доверенного процесса; общего API приложений ещё нет |
| Вычисления | Device/backend interface, память и очередь обычных вычислительных работ | Универсальной абстракции ещё нет; модель не должна определять ABI ядра |

Числа контекста, токенов, слоёв и формат конкретных весов не входят в интерфейс
ядра. Большие файлы/адресные пространства и вычислительная инфраструктура должны
быть проверены заранее на синтетических данных и обычных программах. Поддержка
конкретного устройства — отдельная проверяемая реализация backend/драйвера.

## Текущий шаг: владение файловой транзакцией

В FS3 `fs3_handle_client` принимает доверенный 64-битный идентификатор клиента
отдельно от запроса. Пока транзакция открыта, другой клиент получает busy и не
видит draft, не пишет, не выполняет commit/abort. Текущая реализация сериализует
доступ, а не поддерживает независимые параллельные транзакции. Commit/abort
освобождают владение. `fs3_client_closed` откатывает только открытую транзакцию
названного владельца без дисковых записей и не снимает poisoned-состояние.

С 0.0.19 сервис берёт логическую identity из регистра ответа receive_wait,
заполненного ядром. Kernel broker имеет сессию 0, которая сохраняется при замене
временных fsclient.nos между RPC. Desktop и ребёнок получают разные монотонные ID;
привязка ответа проверяет также сессию, а не только индекс очереди/задачи.
Kernel-authenticated CLIENT_CLOSED подключает callback закрытия к native lifecycle.
Обычный file grant не позволяет подделать это уведомление. Протокол сохранён
также в legacy FS2; источник данных FS3 по-прежнему committed COW roots.

С 0.0.20 есть версионированный журнал native jobs и просмотр Events без модели.
Он не содержит пользовательский текст, не выполняет IO из trap, не позволяет
приложению подделать/стереть запись. Потеря старых записей обнаруживается, два
наблюдателя независимы. Это пока только доверенный controller, не глобальная
шина событий и не выданные будущему агенту административные права.

В 0.0.21 loader читает согласованный snapshot в отдельной private роли, GUI
продолжает работать, Stop закрывает фазу loading, ELF validation остаётся в ядре.
Read snapshot пока сериализует FS, без MVCC. См. [loader.md](loader.md).

Дальше — общий manager, права на конкретные объекты,
постоянный collector/подписки; затем средства приложений/GUI и вычислительных
устройств. Реализованные ограничения и проверки — [jobs.md](jobs.md), [events.md](events.md).

## Условие перехода к ИИ

Обычная тестовая программа без модели должна уметь выполнить делегированную
задачу через системные интерфейсы, получить статусы/события, отменить работу и
пережить отказ исполнителя. Проверяются отказ без прав, чужая транзакция,
устаревшая сессия, отзыв доступа, исчерпание ресурсов и отсутствие побочных
эффектов после отмены. Для поддерживаемых файловых изменений проверяется rollback.

На последнем этапе подключаются веса, tokenizer, алгоритмы запуска и inference
backend, алгоритмы работы с контекстом поверх готового хранилища и логика выбора
действий через уже работающие системные средства. Проверки интеграции остаются обязательными; базовые системные
механизмы к этому моменту уже должны работать независимо от модели.
